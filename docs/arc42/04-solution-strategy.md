# 4. Solution Strategy

## 4.1 Technology Decisions

| Decision | Rationale | Consequences |
|----------|-----------|--------------|
| **Web Components** | Framework-agnostic, standards-based, native browser support | Works with any framework, long-term stability, but requires polyfills for older browsers |
| **Stencil.js** | Best-in-class web component compiler, generates framework adapters, excellent DX | Ties build process to Stencil, but provides tremendous value in code generation |
| **Shadow DOM** | True style encapsulation, prevents CSS conflicts | Components are isolated but can't be styled from outside (by design) |
| **TypeScript** | Type safety, better IDE support, catches errors early | Requires compilation step, but dramatically improves code quality |
| **pnpm Workspace** | Efficient dependency management, fast installs, strict dependencies | More complex setup than npm, but better for monorepos |
| **Adopted Style Sheets** | Efficient theme switching, style composition | Requires modern browser support, but enables powerful theming |
| **SASS** | Variables, mixins, powerful theme authoring | Compilation required, but provides essential features for complex themes |

## 4.2 Top-level Decomposition

KoliBri is structured as a monorepo with clear separation of concerns:

```
┌─────────────────────────────────────────────────────────┐
│                    KoliBri System                        │
├─────────────────────────────────────────────────────────┤
│                                                           │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │  Components │  │   Themes    │  │   Adapters  │     │
│  │   (Core)    │  │  (Styling)  │  │ (Framework) │     │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘     │
│         │                 │                 │             │
│         └─────────────────┴─────────────────┘            │
│                           │                               │
│  ┌─────────────┐  ┌──────┴──────┐  ┌─────────────┐     │
│  │   Samples   │  │    Tools    │  │     Docs    │     │
│  │ (Examples)  │  │  (Tooling)  │  │ (Knowledge) │     │
│  └─────────────┘  └─────────────┘  └─────────────┘     │
│                                                           │
└─────────────────────────────────────────────────────────┘
```

### Component Layers

1. **Core Components** (`packages/components/`)
   - Atomic web components
   - Business logic and accessibility
   - Framework-agnostic implementation

2. **Themes** (`packages/themes/`)
   - Visual styling separate from logic
   - Multiple themes for different design systems
   - CSS/SASS with strict scoping rules

3. **Framework Adapters** (`packages/adapters/`)
   - Auto-generated wrappers for React, Angular, Vue, etc.
   - Framework-specific APIs and patterns
   - Generated by Stencil output targets

4. **Samples** (`packages/samples/`)
   - Example implementations
   - Testing ground for new features
   - Documentation through working code

5. **Tools** (`packages/tools/`)
   - Migration CLI for version upgrades
   - Visual regression testing
   - Development utilities

## 4.3 Architectural Patterns

### Pattern: Composition over Inheritance

- Components are atomic and composable
- Complex UI built by combining simple components
- No inheritance hierarchies, flat component structure

### Pattern: Separation of Concerns

- **Structure/Logic**: Stencil components (TypeScript)
- **Styling**: Theme packages (SASS/CSS)
- **Integration**: Framework adapters (generated)
- **Documentation**: Separate docs site

### Pattern: Five-Layer Styling System

1. **A11y Preset Layer**: Accessibility baseline from `adopted-style-sheets`
2. **Basis Global Layer**: Global component layout (no colors/margins)
3. **Basis Component Layer**: Component-specific layout (no colors/margins)
4. **Theme Global Layer**: Global theme styles (colors, fonts)
5. **Theme Component Layer**: Component-specific theme styles

This layering ensures:

- Accessibility by default
- Themeable without breaking layout
- Clear separation of structure and appearance

### Pattern: Zero Runtime Dependencies

- Components have minimal runtime dependencies
- No heavy framework requirements
- Optimized for bundle size and performance

## 4.4 Quality Strategy

### Accessibility First

- Every component implements WCAG 2.1 AA standards
- Keyboard navigation mandatory
- Screen reader testing for all interactive components
- Automated axe-core testing in CI
- Manual accessibility reviews

### Standards Compliance

- Strict adherence to W3C specifications
- Valid HTML, semantic markup
- Proper use of ARIA attributes
- Progressive enhancement principles

### Performance

- Lazy loading of components
- Tree-shakeable exports
- Minimal CSS footprint
- Shadow DOM for efficient rendering
- Bundle size monitoring

### Developer Experience

- Comprehensive TypeScript types
- Clear, searchable documentation
- Working code examples
- Migration tools for version upgrades
- Framework-specific integrations

## 4.6 Theming Strategy

### Multi-Theming Architecture

Themes are separate packages that can be switched at runtime:

```typescript
import { register } from '@public-ui/components';
import { DEFAULT } from '@public-ui/theme-default';

// Register components with a theme
register(DEFAULT, defineCustomElements);
```

### Theme Structure

- Themes contain only CSS/SASS (no logic)
- Use CSS layers to control specificity
- Minimal CSS custom properties to prevent conflicts
- SASS variables for internal calculations
- Assets (fonts, icons) included in theme packages

### Benefits

- Organizations can create custom themes without forking
- Multiple themes can coexist in one application
- Theme updates don't require component rebuilds
- Design system flexibility
