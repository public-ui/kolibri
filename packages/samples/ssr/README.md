# KoliBri – Server-Side Rendering (SSR) sample

> ⚠️ Server-side rendering with KoliBri builds on the **experimental**
> [`@public-ui/hydrate`](../../adapters/hydrate/README.md) adapter.

This sample is the reproducible reference integration requested in
[issue #5494](https://github.com/public-ui/kolibri/issues/5494) (“Technischer
Durchstich – KoliBri CMS SSR mit z. B. Typo3”). It shows how to render KoliBri
web components **on the server** and ship them to the browser as
[Declarative Shadow DOM](https://developer.chrome.com/articles/declarative-shadow-dom/)
so that users and search engines receive the correct markup **and** the scoped
styles — without running any client-side JavaScript.

## Why this matters

KoliBri components are Stencil web components. Rendered on the client they need
JavaScript to produce their Shadow DOM. In a Content-Management-System such as
TYPO3 — or any classic SSR workflow — we want the finished markup to leave the
server. `@public-ui/hydrate` does exactly that: it runs the components in a
DOM-less Node environment and serializes each component to a
`<template shadowrootmode="open">…</template>` element that the browser upgrades
to a real shadow root natively.

## What the sample does

- `src/ssr.mjs` – the core. It loads `renderToString` from `@public-ui/hydrate`,
  hydrates a small fragment (a `kol-form` containing **`kol-input-text`** and
  **`kol-button`**, plus a `kol-heading`) and wraps the result in a complete,
  standalone HTML document.
- `src/build.mjs` – pre-renders the demo to `dist/index.html` (the `build`
  script). Open that file directly in a browser — no server, no bundler, no JS.
- `src/server.mjs` – a tiny `node:http` server that renders the page on every
  request (the `start` / `serve` scripts), mirroring how a CMS would call the
  renderer per request.
- `test/ssr.test.mjs` – asserts the output really is Declarative Shadow DOM.

## Prerequisites

The hydrate bundle is generated by the `@public-ui/components` build. Build the
dependencies once:

```bash
pnpm --filter @public-ui/sample-ssr build:deps
```

## Run it

```bash
# Pre-render the demo to dist/index.html …
pnpm --filter @public-ui/sample-ssr build

# … or serve it (rendered fresh on every request) on http://127.0.0.1:8080
pnpm --filter @public-ui/sample-ssr serve

# Verify the output is Declarative Shadow DOM
pnpm --filter @public-ui/sample-ssr test:unit
```

Use this from your own code:

```js
import { renderToString } from '@public-ui/hydrate';

const { html } = await renderToString('<kol-button _label="Hello world"></kol-button>');
// html now contains <template shadowrootmode="open">…</template>
```

## The output is Declarative Shadow DOM

The rendered `kol-button` looks like this (styles abbreviated):

```html
<kol-button _label="Hello world" class="… hydrated">
	<template shadowrootmode="open">
		<style>
			/* component-scoped styles travel with the markup */
		</style>
		<kol-button-wc class="… hydrated">
			<button class="kol-button kol-button--normal kol-button--standalone" type="button">
				<span class="kol-span kol-button__text">…<span class="kol-span__label">Hello world</span>…</span>
			</button>
		</kol-button-wc>
	</template>
</kol-button>
```

The browser turns the `<template shadowrootmode="open">` into a real shadow root
without JavaScript, so the component is correct and styled on first paint.

### One required SSR adjustment: revealing the components

Stencil’s hydrate output marks every host element with an inline
`style="visibility: hidden;"`. That is intended for a client runtime that flips
the element visible after hydration — but in a **no-JavaScript** SSR scenario
the components would stay invisible. This sample therefore ships a single CSS
rule in the document `<head>` that reveals already-hydrated components (an
`!important` rule in a stylesheet outranks the non-important inline style):

```css
[class~='hydrated'] {
	visibility: visible !important;
}
```

This is the central implementation finding of the spike: KoliBri components are
SSR-capable today via Declarative Shadow DOM, and the only adjustment needed for
a pure no-JS page is to reveal the pre-hydrated hosts.

## Acceptance criteria (spike)

This sample satisfies the spike when:

- [x] A KoliBri component renders **server-side** through `renderToString` from
      `@public-ui/hydrate`.
- [x] The pre-rendered markup is **Declarative Shadow DOM**
      (`<template shadowrootmode="open">…</template>`) and carries the
      component-scoped styles.
- [x] The page is **correct and visible without client-side JavaScript**
      (verified by `test/ssr.test.mjs`).
- [x] The TYPO3 wiring (HTML Sanitizer + how to embed pre-rendered markup) is
      documented and reproducible.

## Known limitations / follow-ups

- **Hydration is experimental.** Some components rely on browser APIs and may
  emit diagnostics during rendering.
- **Native form submission** of KoliBri forms in a no-JS context is a separate
  concern (see the discussion in issue #5494). This sample renders forms but
  does not change their submit behaviour.
- For **progressive enhancement** you can additionally load
  `@public-ui/components/loader` and register a theme on the client so the
  pre-rendered components become interactive.

### 🇩🇪 Kurzfassung

Dieses Sample zeigt das serverseitige Rendern (SSR) von KoliBri-Komponenten mit
dem experimentellen Adapter `@public-ui/hydrate`. `renderToString` erzeugt
**Declarative Shadow DOM** (`<template shadowrootmode="open">`), sodass Markup
**und** Styles ohne Client-JavaScript korrekt beim Browser und bei Suchmaschinen
ankommen. Voraussetzung ist ein gebautes `@public-ui/components`
(`pnpm --filter @public-ui/sample-ssr build:deps`). Mit `build` wird die Demo
nach `dist/index.html` vorgerendert, mit `serve` pro Request ausgeliefert. Die
einzige nötige SSR-Anpassung: Stencil setzt `visibility: hidden` auf die Hosts;
eine `!important`-Regel im `<head>` macht die bereits hydrierten Komponenten ohne
JavaScript sichtbar. Die TYPO3-Anbindung inklusive HTML-Sanitizer ist unter
[`typo3/`](./typo3/) dokumentiert.
